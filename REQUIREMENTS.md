# Требования: Календарь бронирований

## 1. Обзор

Веб-приложение для бронирования слотов посетителями **без регистрации**.
Администратор через защищённую админку управляет типами событий, периодами
доступности и просматривает бронирования.

## 2. Технологический стек

| Слой              | Технология                          |
|-------------------|-------------------------------------|
| Backend           | PHP 8.x + Laravel                   |
| Админка           | Filament                            |
| Frontend (публичн)| Blade-шаблоны + HTMX                 |
| База данных       | PostgreSQL (или MySQL)              |
| Аутентификация    | Laravel (только для администратора) |
| Деплой            | PHP-FPM + Nginx / Docker            |

## 3. Роли

- **Посетитель** — аноним, без регистрации. Просматривает доступные слоты и бронирует.
- **Администратор** — авторизуется в админке. Полный CRUD над сущностями.

## 4. Функциональные требования

### 4.1 Публичная часть (посетитель)
- FR-1: Просмотр доступных слотов в виде календаря.
- FR-2: Выбор типа события и свободного слота.
- FR-3: Оформление брони с данными:
  - имя (обяз.)
  - email (обяз.) — идентификатор гостя
  - телефон (обяз.)
  - комментарий (необяз.)
- FR-4: Подтверждение брони на странице (без email-уведомления в v1).
- FR-5: Нельзя забронировать занятый/недоступный слот.
- FR-11: Данные гостя запоминаются на клиенте (`localStorage`) и
  предзаполняются при следующем бронировании в той же сессии.
- FR-12: Длинная бронь (несколько последовательных слотов **одного типа**)
  оформляется одной операцией, но сохраняется как **несколько записей броней**
  (по одной на слот), объединённых общим `booking_group_id`.
- FR-13: Горизонт бронирования — **14 дней** вперёд.
- FR-14: Бронирование **на текущий день недоступно**; запись начинается со
  следующего дня.
- FR-15: Брони со статусом `pending` **визуально выделяются** среди
  подтверждённых (`confirmed`) в календаре и админке.

### 4.2 Админка (администратор)
- FR-6: Аутентификация администратора.
- FR-7: CRUD **типов событий**: название, описание, длительность (**15 или 30 мин**),
  цвет, активность.
- FR-8: Управление **периодами доступности**:
  - рабочие интервалы (дни недели, время начала/окончания);
  - исключения/выходные (конкретные даты).
- FR-9: Просмотр списка **бронирований** с фильтрами (дата, тип события).
- FR-10: Изменение статуса/отмена брони администратором.

## 5. Бизнес-правила

- BR-1: **Максимальная суммарная продолжительность бронирований одного
  гостя (по email) за один календарный день — 2 часа.**
  Отменённые (`cancelled`) брони не учитываются.
- BR-2: Слот не может пересекаться с другой активной бронью
  (статусы `pending` и `confirmed` занимают слот).
- BR-3: Бронирование возможно только внутри периодов доступности и вне исключений.
- BR-4: При длинной броне создаётся несколько записей `bookings`, объединённых
  общим `booking_group_id`; лимит 2 часа применяется и суммарно, и к
  непрерывной последовательности слотов одного типа.
- BR-5: Длительность слота и шаг сетки — **15 или 30 минут**.
- BR-6: Новая бронь создаётся в статусе `pending` и **сразу занимает слот**;
  требует подтверждения администратором.
- BR-7: При отмене/отклонении брони админом слот **автоматически освобождается**.

## 6. Нефункциональные требования

- NFR-1: Валидация на фронтенде — **email** и **телефон (российский формат
  `+7 (XXX) XXX-XX-XX`)**; на бэкенде все проверки **дублируются**.
- NFR-2: Защита админки авторизацией и CSRF.
- NFR-3: Отзывчивый интерфейс (mobile-friendly).
- NFR-4: Прохождение линтера и тестов (CI через GitHub Actions уже настроен).
- NFR-5: Защита от **SQL-инъекций** (Eloquent ORM / prepared statements) и
  **XSS** (экранирование в Blade).

## 7. Модель данных (черновик)

**guests** (гость по email)
- id, email (unique), name, phone, timestamps

**event_types**
- id, name, description, `duration_minutes ∈ {15, 30}`, color, is_active, timestamps

**availability_rules** (регулярная доступность)
- id, weekday (0–6), start_time, end_time, timestamps

**availability_exceptions** (выходные/исключения)
- id, date, is_closed (bool), start_time (nullable), end_time (nullable), timestamps

**bookings**
- id, event_type_id (FK), guest_id (FK), booking_group_id (nullable, UUID),
  starts_at, ends_at, comment,
  status (pending/confirmed/cancelled), timestamps
- Примечание: одна запись = один слот; длинная бронь = несколько записей с
  общим `booking_group_id`.

## 8. Вне области v1

- Регистрация посетителей.
- Email/SMS-уведомления (запланировано на будущее).
- Онлайн-оплата.
- Мультиязычность.
- Экспорт бронирований (CSV и т.п.).
- Несколько администраторов (в v1 — один админ).

## 9. Подтверждённые решения

- D-1: Лимит 2 часа — **на одного гостя (по email)**. Гость заводится в БД по email.
- D-2: Один слот = одна бронь. Длинная бронь = несколько броней с общим
  `booking_group_id`.
- D-3: Часовой пояс приложения — **Europe/Moscow**.
- D-4: Посетитель **не может** отменять/переносить бронь в v1 (только администратор).
- D-5: Данные гостя хранятся на клиенте в `localStorage`, привязка к сессии.
- D-6: Горизонт бронирования — **14 дней**; текущий день недоступен, запись
  начинается со следующего дня.
- D-7: Длинная бронь набирается **последовательными слотами одного типа**.
- D-8: В v1 — **один администратор**, экспорт бронирований не требуется.
